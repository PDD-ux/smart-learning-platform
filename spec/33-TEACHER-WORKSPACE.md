# 教师端职责与工作区规格（§29.16–§29.19，2026-10-21）

> §29.16确认职责边界；§29.17已落地 `teacher` 账号、登录与服务端归属权限；§29.18已落地教师专用页面和导航；§29.19已实现学习通式课程中心。当前业务库没有旧班级，未执行移交；正式单班级移交仍未实现。§29.11最终三主线原生验收保持未完成。

## 1. 目标与范围

把课程教学操作从平台管理员工作区移到教师工作区，使毕设演示中的管理员、教师、学生各有清晰入口。三条核心业务继续是资料学习与智能笔记、班级课程与作业、智能批改与错因诊断；教师端是第二条业务的工作区，不增加第四核心或另建教务系统。

首版只支持管理员创建教师账号；公开注册仍只产生学生。管理员登录到 `/admin`，教师登录到 `/teacher`，学生登录到 `/dashboard`。管理员只使用密码登录；教师和学生可在独立授权后使用人脸登录，成功后写入本人每日记录。教师通过 `/teacher/attendance` 管理本人模板和打卡；这不授予教师访问全站签到、他人模板或学生私人数据的权限。学生既有页面与原模板流程保持。

## 2. 职责划分

| 角色 | 可以做 | 不可以做 |
| --- | --- | --- |
| 平台管理员 | 账号与角色管理、平台总览、既有签到记录查询、讨论举报处理；管理自己历史创建的班级直至显式移交 | 凭管理员身份读取其他教师班级的提交正文、评语、私人学习资料或人脸模板；替教师自动给分 |
| 教师 | 创建并管理本人负责的班级、邀请码和成员；发布章节、任务及截止时间；查看本班正式提交与真实统计；批阅、退回和写评语；按原授权流程发布本人资料的共享副本并绑定班级；本人授权后使用人脸登录、查看/删除本人模板和本人每日打卡 | 管理全站账号/签到/举报；读取其他教师班级、学生未交草稿、个人笔记、私人AI批改报告或他人的人脸数据 |
| 学生 | 学习本人资料、加入班级、阅读已发布章节、提交本人作业、查看本人反馈及私人智能批改建议 | 管理班级成员、发布任务、批阅他人作业或查看同学私人学习记录 |

“教师”是全局登录角色，但教学数据权限仍逐班级核对 `Classroom.responsibleId`。同一教师可负责多个班级；另一个教师及管理员都不能仅凭角色读取该班级作业全文。学生加入仍需要有效邀请码；共享课程公开副本与班级成员权限保持独立，绑定课程不公开原始私人资料。

## 3. 页面与操作迁移

- `/teacher`：只呈现本人班级数、待批阅数、最近任务及进入班级的操作，不使用全站账号数或人脸签到作为教学指标。无班级时给出创建入口；教师从“打卡与人脸”进入本人设置页。
- `/teacher/classes` 及详情、任务与提交页：承接现有 `/admin/classes` 中的班级创建、邀请码、成员、章节、任务、提交看板和批阅。保持现有文字/附件版本、截止、退回重交与正式评分行为；桌面分栏、窄屏单列。
- 教师的共享课程准备与发布：复用现有“本人资料→授权声明→独立副本→核对预览→明确发布”流程。公开给登录用户的副本须继续提示传播范围；班级章节只能绑定已发布的授权副本。首版不增加新的全站审核流。
- `/admin` 保留平台管理总览、用户管理、签到记录、讨论举报；新教师功能可用后，管理员侧栏移除“班级课程”和教师的共享课程发布入口。旧地址不能直接让无权角色访问；用户已打开的管理页需有明确去向和草稿保护。
- 学生 `/classes`、`/homework` 及学习中心保持原归属。本人AI批改建议与教师正式评分仍分别显示，不自动同步或代写分数。

## 4. 角色、旧数据和权限迁移

1. `User.role` 目标允许 `student | teacher | admin`。管理员用户管理增加“教师”选项；自助注册及普通用户接口不能自行提升角色。人脸登录、模板和个人打卡仅允许数据库当前student/teacher，管理员人脸登录统一拒绝；每次受保护请求在数据库核对当前角色，旧 JWT 中的角色声明不单独授予教师或管理员权限。
2. 新建班级只允许当前 `teacher` 创建并成为 `responsibleId`。教师仅能读写自己负责的班级；已移除或退出的学生只保留既有历史可见范围。所有创建、发布、批阅、移交维持现有并发、幂等和审计要求。
3. 已存在的管理员负责班级保持原 `responsibleId` 和原数据。过渡期仅该原负责人可从兼容入口管理本人旧班级，不开放新建管理员班级；不批量改账号角色、班级负责人、提交/成绩或共享副本归属。
4. 若需把旧班级交给教师，另设由原负责人及平台管理员明确确认的单班级移交操作，并在一个事务内检查目标教师、班级状态与版本、记录审计；移交前后均验证附件与历史批阅读取范围。首版若不实施移交，旧班级继续走上述兼容入口，不伪称已迁移。
   现有数据库将 `AssignmentReview(classroomId, reviewerId)` 外键绑在 `Classroom(id, responsibleId)` 上；已有批阅的班级直接改 `responsibleId` 会被数据库拒绝。正式移交前须另做窄迁移：历史批阅人独立关联User且保留版本/班级外键，事务重核对历史与新负责人；绝不能临时关闭外键或改写旧批阅人。
5. 教师账号的删除或降级若仍负责班级、发布课程或待批阅提交，必须先阻止并给出处理入口；不靠级联删除清掉作业、评语或附件。管理员也不得以全局角色绕过班级归属读取学生正文。

§29.17–§29.18实际入口：教师登录进入 `/teacher`，通过 `/teacher/classes`、`/teacher/assignments`、`/teacher/courses` 管理本人班级/任务和授权副本；`GET /api/teacher/overview` 仅汇总本人班级、任务和正式待批阅计数。现有 `/api/admin/courses` 的课程管理操作按数据库当前角色及 `publisherId` 授权教师本人副本，不因此授予其他 `/api/admin/*` 平台管理权限。管理员侧栏保留清楚标注的旧班级兼容入口，管理员课程治理只能下架已发布副本；公开课程读取仍遵守发布状态。

## 5. 实施与验收边界

先完成角色/权限与兼容接口，再接教师页面和导航，最后更新 §29.11 的三角色原生演练。实现时同步 `spec/02-DESIGN.md`、`spec/03-ARCHITECTURE.md`、`spec/04-DATA-MODEL.md` 和 `spec/06-VISUAL-SPEC.md` 的实际页面、DTO、权限矩阵；需要迁移时使用窄迁移并保护旧表和历史记录。

最低验收：管理员创建教师账号；教师登录并创建班级；两名学生加入、提交、退回重交、收到教师正式批阅；教师 B/普通管理员/学生尝试直达他班提交均被拒绝；教师不能调用全站用户管理、签到列表或举报接口；老管理员班级仍由原负责人可读且不会自动移交；学生和教师人脸登录及本人模板/打卡可用，管理员人脸登录与接口被拒绝；学生个人批改记录不受影响。工程回归、真实数据库/接口、桌面与手机原生页面分别记录；不把页面可打开或 HTTP 200 当作权限验收。

## 6. §29.18 实施记录

教师总览页显示本人班级、正式待批阅和最近任务；本人班级/任务提交批阅/授权课程资料入口均使用独立 `TeacherShell`，直接访问时校验当前profile角色。教师任务链接保持教师路由；共享的班级与作业组件按入口选择路由基址，不复制业务逻辑。管理员导航移除教师课程发布入口，保留平台治理及旧班级兼容入口；旧 `/admin/courses` 仅可治理已发布副本。管理员人脸登录被拒绝，教师与学生个人人脸设置使用各自角色工作区入口。

新增只读 `GET /api/teacher/overview` 汇总接口，不返回提交内容、附件、评语或草稿。没有数据库迁移或新依赖。项目质量检查中TypeScript类型检查、ESLint和生产构建通过；本地浏览器当前未登录，原生页面、多角色直达URL及窄屏实际页面点验保留到§29.11统一演练。当前数据库班级0、正式批阅0，故无旧班级移交数据。


## 7. §29.19 学习通式教师课程中心

用户确认教师端以课程为中心组织。首页先列本人负责课程的卡片，点击后进入课程空间，在同一课程下找章节、作业及学生/邀请码；作业批阅继续提供跨课程待办。“我的课程”对应当前`Classroom`记录，学生仍以邀请码加入；“课程资料”只代表独立的授权共享副本准备与发布入口。此调整只重排现有入口并展示真实已有数据，不引入课程表、教学互动类型或额外统计。

课程详情增加教师可见的概览展示，计数只从当前已读取的成员、章节、任务数组计算；加载/失败时不展示为零。现有章节发布、作业提交/批阅、成员管理、邀请码、班级编辑/归档完全复用，权限仍由服务端当前角色和`responsibleId`验证。管理员旧班级兼容界面与学生界面保持原名称及交互；屏幕窄时卡片单列，课程空间操作按顺序堆叠。
